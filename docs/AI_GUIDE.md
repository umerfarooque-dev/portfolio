# Portfolio AI Development Guide

The operating manual for an AI agent working on this codebase. Read this before touching
anything.

---

## Before modifying anything

1. Read **`docs/CONTEXT.md`** — the project in one page.
2. Read **`docs/PROJECT_MAP.md`** — which directory owns what.
3. Read **only the one or two topic docs** your task touches
   (`COMPONENTS.md`, `DATA_MODEL.md`, `DESIGN_SYSTEM.md`, `ANIMATIONS.md`, `SEO.md`,
   `SECURITY.md`, `ARCHITECTURE.md`).
4. Identify the **smallest set of files** that must change.
5. Open only those files.

**Do not scan the whole project.** That is what this documentation exists to prevent. If a
doc is wrong or missing something, fix the doc as part of your change.

### Also read the framework docs

Next.js 16 differs from most training data. `AGENTS.md` requires it and so does this guide:
read the relevant page in **`node_modules/next/dist/docs/`** before writing framework code
(routing, metadata, caching, `next/image`, server actions, `sitemap.ts`, `opengraph-image`).
Heed deprecation notices. Don't guess an API.

## Rules

**Design**
- Preserve the existing design language. Read `DESIGN_SYSTEM.md` first.
- **There are two design systems in this repo** (current lime-on-black, and a legacy
  sky/purple one on `/projects*` and `/contact`). Match whichever the file you are editing
  already uses. Converting between them is a redesign — only on explicit request.
- Change design **tokens** in `globals.css` `@theme`, not individual components.
- Never add a `tailwind.config.js`.

**Code**
- Reuse existing components. Check `COMPONENTS.md` before creating anything.
- Do not create duplicate components.
- Do not introduce a dependency without a stated reason. Three animation libraries is the
  ceiling.
- Do not rewrite working code. Prefer the smallest diff that solves the problem.
- Follow existing naming: PascalCase component files, named exports, `use`-prefixed hooks.
- Follow the existing folder structure: primitive → `atoms/`, page section → `organisms/`,
  pure logic → `lib/`, React-dependent logic → `hooks/`.
- Match the surrounding comment density. This codebase explains *why*, not *what* — do the
  same.
- Do not modify unrelated files.

**Content**
- **Never hardcode content.** Every string, URL, project, post and social link belongs in
  `src/data/`. See `DATA_MODEL.md`.
- Never invent statistics, testimonials, client names or project URLs. `stats` is empty
  because fabricated numbers had to be removed once already.
- Verify a project URL resolves before adding it.

**Correctness**
- Keep server components server. Add `"use client"` only for hooks, state, refs or browser
  APIs.
- Never import `src/lib/hero-slides.ts` from a client component — it uses `fs`.
- Never import React into `src/data/`.
- Import Prisma types from `@prisma/client`, never from `@/generated/*`.
- Register GSAP plugins only in `src/lib/gsap.ts`.
- Every animation must honour `prefers-reduced-motion` — use `usePrefersReducedMotion()`
  for JS, `motion-safe:` for CSS.
- If you add a form field, add it to the matching Zod schema. Zod strips unknown keys
  silently.

**Verification**
- Check responsive behaviour after any UI change (320px → 1920px).
- Check accessibility after any UI change (contrast, focus, one `<h1>`, labels).
- Run the full check before claiming done:
  ```bash
  npx tsc --noEmit && npx eslint src && npm run build
  ```
  All three are currently clean. Leave them clean.

## Workflows

### A small change

1. Read `AI_GUIDE.md` (this file) and `PROJECT_MAP.md`.
2. Identify the owning component or data file — use the lookup tables in `PROJECT_MAP.md`
   §"where do I change X" and `DATA_MODEL.md` §"Quick lookup".
3. Inspect only that file and its direct dependencies.
4. Make the minimal change.
5. Run `npx tsc --noEmit && npx eslint src`.
6. Report: files changed, what, why, side effects, checks run.

**Example:** *"Change my email address."*
→ `src/data/site.ts` → `SITE.email`. One file. Everything else reads from it.

### A new feature

1. Understand the existing architecture (`ARCHITECTURE.md`).
2. Look for reusable components (`COMPONENTS.md`) — do not rebuild what exists.
3. Decide where it belongs: new route → `src/app/`, new section → `organisms/`, new content
   → `src/data/`.
4. Check the bundled Next.js docs for any framework API you will use.
5. Implement, following the design system and the existing patterns.
6. Test responsive behaviour at 320 / 768 / 1280 / 1920.
7. Test accessibility: contrast, keyboard focus order, one `<h1>`, labels, reduced motion.
8. Run `npx tsc --noEmit && npx eslint src && npm run build`.
9. **Update the docs** — at minimum `COMPONENTS.md` or `DATA_MODEL.md`, plus `CHANGELOG.md`.
   If the architecture changed, update `ARCHITECTURE.md` and `CONTEXT.md`.

### A bug fix

1. **Reproduce it.** `npm run dev`, or `npm run build` for prerender and type failures.
   `next dev` forwards browser console errors to the terminal, and `/_next/mcp` exposes
   `get_compilation_issues` and `compile_route`.
2. Identify the **root cause**, not the symptom. Check `ANIMATIONS.md` §"Debugging
   checklist" for animation issues — most have a known cause.
3. Find the owning component.
4. Fix the root cause. Resist adding a workaround on top of working code.
5. Test the related functionality, not just the one broken case.
6. If behaviour or architecture changed, update the docs and `CHANGELOG.md`.

### Content update

1. Find the file in `DATA_MODEL.md` §"Quick lookup".
2. Edit only that data file.
3. If you added an image, run `npm run images`.
4. `npm run build` to confirm the new content prerenders.

**You should almost never touch a component to change content.** If you think you must, the
content probably needs moving into `src/data/` first.

## Before changing a component, state

- What the component currently does
- What depends on it (`COMPONENTS.md` lists "Used by")
- Which files will change
- Why each of those files needs changing

## After changing code, report

- **Files changed**
- **What** changed in each
- **Why**
- **Potential side effects** — especially other consumers of a shared file
- **Checks performed** — the actual commands and their results

Report failures honestly. If a check did not pass, say so and show the output. If you
skipped something, say that too.
